# FatLine Android client parity tracker

This is a **functional client parity** checklist, not a mandate to simulate physical radio scanner hardware.
The baseline is the ThinLine Android app's **useful network, playback, channel, history, alert and account features**. A handheld-style scanner facade is optional and not a parity gate. Verify each relevant behavior on an Android device
against a third-party/self-hosted compatible scanner; a passing JVM/build CI job is
**not** an end-to-end test.

References (public feature descriptions only; FatLine does not transmit analytics,
account information, or encryption keys to ThinLine-hosted services):
- [ThinLine Android Play listing](https://play.google.com/store/apps/details?id=com.thinlinedynamicsolutions.ohiorsn)
- [ThinLine v26.10.01 release description](https://newreleases.io/project/github/Thinline-Dynamic-Solutions/ThinLineRadio/release/v26.10.01)

**Recent playback gate:** The UI reads only `recentCalls`; socket CALL receipt changes archive and `lastCall`, never Recent. Media3 must see the item start and its position advance before an automatic transition/end can add it. A quick device acceptance check is to accumulate queued calls while another call is playing: pending calls must not appear in Recent until each actually plays through. Test again with audio stopped and then resumed; the list must not grow just from received calls. The service does not persist Recent across process recreation.

**FatLine-specific lock-screen call details:** Android's global sensitive-content setting stays unchanged. Because the user explicitly wants FatLine's radio traffic visible on the locked screen, FatLine itself requests `VISIBILITY_PUBLIC`, with the same detailed BigText foreground notification while silent and while audio is playing. Only the currently playing transmission contributes talkgroup title, server, system, TG ID, queue count, and an optional bounded transcript excerpt; idle/reconnecting state never inherits stale call text. Anyone with access to the lock screen may see these FatLine details, but other apps retain their existing privacy behavior. Android still determines whether to display a full notification card or just its icon; verify on the device. No second notification, session, polling or external traffic.

**Single stable scanner notification throughout playback:** #131–#133 tried switching between an ordinary foreground notification while idle and `MediaStyle` while playing. On the user's Pixel 9a, #133 instead produced a scanner/star icon only when idle and **no visible notification at all during playback**. The app no longer switches category or notification style during calls. It owns one ongoing `CATEGORY_SERVICE` BigText notification, consistently updates the current call and tag accent on the same foreground ID, and presents existing Skip, Clear queue and Disconnect actions. The `MediaLibrarySession` remains available for Android Auto, but is not attached to this foreground notification as MediaStyle. New calls on the same TG force an update through the playing media ID; no extra notification or audio polling. Existing non-badging silent DEFAULT channel and app-wide notification privacy remain unchanged. Pixel lock-screen card versus icon still requires device testing.

**Earlier lock-screen media-style experiment (superseded):** #131 introduced a Media3-linked `MediaStyle` notification and a DEFAULT-importance, soundless, non-vibrating, non-badging notification channel to try to match ThinLine's media card. Follow-up reports on this device showed that switching to MediaStyle during radio playback hid the notification, so the stable service-style notification now replaces that experiment. The active Media3 `MediaLibrarySession` still provides Android Auto functionality.

**Lock-screen visibility troubleshooting and stable scanner card:** Android owns notification display even when FatLine posts the foreground service indicator. Settings now expose the effective FatLine app/channel notification status and a direct link to Android's existing Scanner playback channel (or app notification settings before the channel exists), plus a reminder to enable silent notifications on the lock screen. The scanner card reserves a fixed HUD call-detail footprint and Call actions row so call arrival/completion no longer shifts the rest of the controls vertically; the queue may still intentionally expand on request. No second notification, extra wakeup, new permission or audio behavior change.\n\n**Restored full-background talkgroup coloring:** On the user's Pixel 9a, switching to accent-only in #135 removed talkgroup coloring entirely on the lock screen. At the user's explicit request, the foreground scanner notification once again uses `setColor(tagColor).setColorized(true)` to fill the card with the active talkgroup's tag color. The existing tag-color source respects user overrides. No active call or missing tag yields a neutral system notification. Keep the working single `CATEGORY_SERVICE` foreground notification, real call details, queue status and Skip/Clear/Disconnect actions intact; do not reintroduce a MediaStyle notification.\n\n**Lock-screen scanning indicator:** While one or more scanner profiles are active, the existing foreground playback notification doubles as a public lock-screen status indicator, using the same notification ID and no added push service, network traffic, or launcher badge. It shows **FatLine · Scanning** when connected, **FatLine · Connecting** when awaiting a connection, and **FatLine · Monitoring** when all connected scanners have live audio paused. Current call titles appear only while audio is actually playing. Multiple scanner connections are counted without exposing saved PINs, transcripts or private server URLs. Notification content and Android channel request PUBLIC lock-screen visibility; Android's per-app and lock-screen notification settings can still hide them. Stopping all scanning removes the foreground indicator as before.\n\n**Audio-cache filesystem and eviction pass:** The existing per-scanner cache cleanup cadence is unchanged (first buffered call and then once per 16 writes). Sorting files by `lastModified()` used to query file metadata inside the comparator, repeatedly performing filesystem stats for the same audio file. `PlaybackCachePolicy.newestFirst()` now reads each modification time once and performs the same stable newest-first sort in memory. During a sweep, one direct pass skips queue-protected paths and deletes only unprotected files beyond the existing newest-150 limit, without creating intermediate path lists, a filtered list, a set of eviction paths, or another filtered file list. The protected-path set is still loaded fresh from the persisted playback journal on each sweep; ties and retention semantics are unchanged. Tests compare ordering and eviction against the old reference implementation across large caches, pinned files, and retention limits. This reduces expensive metadata reads and allocations but does not yet establish a measured battery difference.

**Active talkgroup color lookup cache:** The ongoing scanner foreground notification is refreshed for queue, connection and metadata updates even when the same transmission continues playing. Instead of repeatedly traversing systems/talkgroups to resolve the same tag color, the service caches the result by Media3 media ID, immutable call object, systems-list identity and tag-color-map identity. A new transmission, replaced tag configuration or altered call metadata immediately recomputes it; silence, disconnect or missing config clears stale tints. The existing `setColorized(true)` full-background look and user overrides remain unchanged. Regression tests cover 150 unrelated scanner updates without duplicate resolution and changes to all invalidation inputs. No notification count, timing, network traffic, Media3 session or audio behavior changed; actual CPU benefit unmeasured.

**Stable Compose theme and navigation:** FatLineApp now remembers its app-wide `ColorScheme` by resolved user/site accent and caches accent parsing by the two actual source settings, so frequent scanner call, queue, listener and history StateFlow updates do not allocate a new theme object when the theme has not changed. Primary and More navigation lists are static shared values instead of allocations on every root recomposition. Theme still updates immediately when the configured site or user accent changes and all tabs remain in their original positions. No change to the user-preferred full-color lock-screen *notification* (separate Android UI), background monitoring, or network behavior. Real-device frame, heap, and battery impact is unmeasured.

**Source metadata fast path:** Incoming calls with zero or one structured radio source now skip building a sorted JSON list, a duplicate-ID set and two mutable result lists. These cases read the source and optional tag directly, while retaining the legacy `source` fallback, configured unit aliases, source-tag precedence and position handling. The existing multi-source sorting/deduplication remains unchanged. Unit tests cover blank, malformed and single-source payloads, fallback IDs, alias resolution and priority, alongside the existing ordered multi-source tests. No network, notification, scanner subscription, queue persistence or alert changes; on-device savings unmeasured.

**Low-allocation scanner queue pruning:** Filtering queued calls after channel-subscription changes and removing live media for paused scanners previously split every Media3 ID into several substrings. The scanner service now reuses each media ID and applies delimiter scans via `PlaybackQueuePolicy.liveChannelForProfile` and `isLiveCallForProfile`. System and talkgroup numbers are still parsed only for genuine live media in the matching profile. Tests compare against independent previous split parsers for malformed, replay, whitespace, extra-separator and multi-profile cases. Reverse iteration, currently playing cancellation and queue item removal semantics remain unchanged. No network, alert, lock-screen color, queue journal or timing changes; CPU impact unmeasured.

**Queue ID parsing and Android Auto library allocations:** Live-call dedup checks run when accepting transmissions or recovering queue state. Instead of splitting each candidate Media3 identifier into seven separate strings, FatLine now scans fixed delimiters and parses only the profile/call ID while preserving the exact seven-part shape and signed/numeric validation; tests compare the old parser across malformed, alternate-format and many valid IDs. Rebuilding Android Auto favorite channels also uses a single nested iteration rather than filter/flatMap/filter/map intermediate lists. Favorites still preserve system order, talkgroup order, hidden systems, titles and IDs; large-configuration tests independently compare the old algorithm. No extra requests, subscription changes, notification changes, new timers or additional persistent data. These are structural allocation reductions, not yet measured phone CPU/battery savings.

**Archive sorting and idle publication allocation pass:** Paged archive History and multi-scanner aggregate History used a comparator that reparsed each call's ISO timestamp on *every comparison*. `HistoryTimestampSortPolicy` now computes exactly one timestamp per call, performs a stable ascending/descending sort of precomputed keys, and retains the previous invalid-date timestamp=0 fallback and duplicate-ID behavior. The single-scanner newest-first fast path still reuses its immutable list. `ScannerRepository.publish()` also checks existing immutable per-profile snapshots *before* constructing a map on passive no-change callbacks, while retaining the existing post-snapshot membership/equality guard. No new timers, requests, queue writes, media transitions, UI changes, or network traffic. These are structural reductions in parsing/allocation, not measured battery or CPU savings; regression tests cover long archives, ties, ascending/descending ordering, invalid dates and one timestamp parse per item.

**WebSocket/UI publication pass:** Repository `publish()` now skips state aggregation and flow publication when all immutable per-server snapshots are unchanged, while changes to any server or profile membership continue through the existing flow semantics. Android Auto's foreground-service collector now skips unchanged favorite configurations without allocating a union set or temporary result objects on each scanner event, and releases entries when profiles are removed. Tests cover zero-change frames, reconnect/status updates, favorites, removals and same-sized profile replacements. No WebSocket protocol frames, audio callbacks, queue persistence, notification cadence or transcript polling intervals changed. Actual CPU/battery impact is not yet measured.\n\n**Polling work elimination:** Foreground transcript monitoring keeps the existing 30/60-second HTTP cadence, but an in-memory, strictly bounded exact-text snapshot avoids re-running keyword normalization/matching for unchanged calls on each page. Reviewed transcripts and updated labels still re-run, settings changes create a new cache, and failures remain retryable. Each 5-minute NWS cycle still fetches current warnings but does not rewrite SharedPreferences if the active warning-ID set is unchanged. No notification or network frequencies were altered; real-device CPU/battery effect is unmeasured.\n\n**Background CPU pass:** Ignore duplicate server version/listener-count messages before allocating/publishing scanner state; avoid system/talkgroup lookups when no group/tag History filter is selected; skip configured unit-alias search when the call supplies a higher-priority source tag; and render zero- or one-source calls without building temporary lists. A large independent regression matrix checks History filter equivalence across filters, invalid dates and missing talkgroups. These are structural savings, not measured reductions in battery usage.\n\n**Memory/allocation audit:** Cached alert badge keys are reused while immutable alert lists remain unchanged and disconnected profiles are released from the cache. Audio-cache path naming now uses ASCII checks instead of per-call regex compilation. Pending call metadata is removed when Android rejects both normal and foreground service starts. These reduce allocations/exceptional retention without altering call, alert, playback or archive limits. The user's 44.4-minute representative capture averaged 3.7% CPU of one core; PSS went from 174.2 to 192.9 MiB (205.7 MiB peak). This is not proof of a leak or of a measured improvement.\n\n**Performance acceptance:** The playback-service playlist is projected with one media-ID lookup per item rather than repeated full-list allocations; queue overflow and reconnect duplicate checks read media IDs lazily. Unit tests compare queue contents, playing item, overflow index and deduplication against independent pre-change logic. This is a structural reduction in traversals/allocations, **not** a measured battery or CPU improvement. Confirm no regressions on a physical Android device with long replay queues, background playback, reconnects, skips and recovery.

## Deliberately excluded by user request

- **Physical scanner keypad, simulated signal meter and scanning sweep**: not required; this is a streaming client, not a hardware scanner emulator.
- **Push alerts** and native remote-push registration: not required for this FatLine parity target. Local notifications from received or polled transcript text are allowed and replace server-alert notifications when explicitly enabled.
- Server-URL validation during setup and a dedicated AI-summary UI are not required.
- ThinLine subscription/advertising flows, duplicate ads, or app-side analytics/tracking: not added.
- ThinLine-hosted account or relay calls: blocked by existing privacy policy.

## Shipping gate

Every parity PR must pass structural validation, unit tests, APK build and stable signing in
GitHub Actions, then be merged. All assertions about **actual Android behavior** additionally
require physical-device and compatible-server verification; keep those marked unverified until tested.
